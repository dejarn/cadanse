# Vision

_Last updated: 2026-05-26_

## Problem

Dance teachers manually manage student lists, classes, and shows. Building a performance order that respects the constraint "no student performs in two consecutive acts" is tedious by hand. Cadanse automates this management and the generation of the performance order.

## Out of scope

- Payment and fee management
- Absence tracking and rehearsal scheduling
- Direct communication with students
- Multi-school support (one instance = one school)

## Core concepts

| Concept | Definition |
|---|---|
| **Season** | Academic year spanning two calendar years (e.g. `2025-2026`). One season is active at a time; others are archived. |
| **Student** | Person enrolled in the school, assigned to classes for a given season. |
| **Class** | Recurring dance class identified by a name, a time slot (day + time), and a teacher, within a season. |
| **Show** | Performance event linked to a season. Multiple shows possible per season. |
| **Act** | Choreography performed at a show. Optionally associated with a class. One class can produce multiple acts. Acts contain ordered scenes with student stage placements. |
| **Participation** | `ShowParticipation` (student × show) and `ActParticipation` (student × act). Act participation created automatically for all students in the act's class. Removing the row = student excluded from that act. No boolean flag — row existence = included. |
| **Performance order** | Ordered sequence of acts for a show, generated by algorithm and validated by an admin. |
| **Public link** | Short URL providing read-only access to a show's performance order without authentication. |

## Roles

| Role | Scope |
|---|---|
| **Super-admin** | Single hardcoded account. Creates and manages admin accounts. |
| **Admin** | Full access to all school data (students, classes, shows, acts, performance orders). |
| **Public** | Read-only access via short link only. |

## Major views and usage modes

1. **Student management** — CRUD, assignment to classes per season.
2. **Class management** — CRUD, teacher and time slot association.
3. **Show and act management** — show creation, act add/edit, participation management.
4. **Performance order generator** — constraint configuration, generation, manual adjustment, validation.
5. **Roll call page** — list of students enrolled in a class for the current session; not persisted, helps the teacher at the start of class.
6. **Public view** — show performance order accessible via short link, updated in real time (SSE) to track progress on the day of the event.

## Performance order algorithm — rules

The algorithm respects constraints in the following priority order:

1. **Fixed positions** — certain acts are pinned to a specific index (e.g. opening act, closing act).
2. **Maximum spacing** — maximize the number of acts between two appearances of the same student (soft constraint, best-effort).

When constraints conflict, fixed positions take precedence, then spacing.

## Active season

The active season is detected automatically and can be changed manually by an admin. Past seasons are archived and fully read-only — no edits allowed on any data belonging to an inactive season.

## Accepted trade-offs

- The roll call page is not persisted (ephemeral).
- The algorithm is best-effort: when constraints are highly restrictive (many fixed positions combined with students concentrated in few acts), optimal spacing is not guaranteed.
- The application targets a very small audience (1–2 admins); significant load occurs only when the performance order public link is shared (potentially several dozen simultaneous viewers).
- `currentPosition: null` means "show in progress" when set, nothing otherwise — no distinction between "not yet started" and "finished". Intentional simplicity.
